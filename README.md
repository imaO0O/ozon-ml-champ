# E-CUP 2026 — задача 3: ценность пользователей Поиска

Предсказание суммарного GMV пользователя за 30 дней (14.02.2026 — 15.03.2026)
по дневному логу активности в Поиске и Каталоге. Метрика — RMSLE.

## Данные

Скачать со страницы соревнования и положить в `data/raw/`:

```
data/raw/train.parquet        172 МБ, 30 631 006 строк, 2025-01-01 .. 2026-02-13
data/raw/sample_submit.csv    250 000 user_id
```

Лог **прорежен**: строки есть только за дни с активностью. Полную сетку
`user x day` (≈100 млн строк) нигде не разворачиваем — все оконные агрегаты
считаются одним ленивым `group_by` в polars.

Если данные лежат вне репозитория, путь можно задать переменными окружения
`OZON_TRAIN` и `OZON_SUBMIT`.

## Запуск

Рабочий путь целиком — от признаков до откалиброванного сабмита:

```bash
python -u src/datasets.py --test                                  # признаки по всем срезам (кэш в data/processed)
python -u src/train.py --cutoffs 6 --ensemble --final --name lgbm_ens
python -u src/predict.py --name lgbm_ens                          # сырой сабмит в submissions/
python -u src/probe_shift.py --derive-shift --source <сырой>.csv  # сдвиг: бесплатно, без сабмита
python -u src/probe_shift.py --source <сырой>.csv --delta <выведенный> --out shifted.csv
```

Последние две строки — калибровка, она дала на лидерборде больше, чем все
улучшения модели вместе взятые (0.0035, см. раздел 3 в [PLAN.md](PLAN.md)).

**Поправки индивидуальны для каждой модели, не копируйте чужие числа** — но
две из трёх теперь считаются, а не меряются. Сдвиг выводится бесплатно из
известного уровня тестового окна. **Растяжение считается офлайн** из целевой
дисперсии: `α* = sqrt(2.6408 / Var(log1p(предсказание)))`, проверено на
**восьми** измеренных значениях α от 1.0122 до 1.0572, разброс цели 0.29%;
последняя проверка предсказала вклад до седьмого знака (PLAN.md, раздел 3).
Итого новая модель стоит **одного** сабмита вместо трёх.

**Кривизна: перенос работает не всегда, и это измерено.** На одиночной модели
перенос γ = −0.0174 с похожей брал около 90% и стоил +0.00059 на лидерборде.
На **составе** (наша половина плюс половина трека C) тот же перенос дал
**+0.0000024**, то есть ноль: у смеси с моделью другого устройства своя
структура ошибки и своё оптимальное γ. Переносить можно внутри одного
семейства, на состав — нельзя.

**Калибровать всегда последним действием.** Смесь двух уже откалиброванных
файлов разбавляет обе поправки: при корреляции меньше единицы дисперсия смеси
ниже целевой, и то же происходит с кривизной, если у второй половины её нет.
Недобор реальный — у одного из полученных от трека C файлов он стоил 0.00056,
у другого не был выставлен уровень, и это стоило 0.00243.

**Пересборка финального файла:** `python -u src/rebuild_final.py` повторяет
цепочку смесей и калибровки из компонент в `submissions/` и **сверяет
результат с отправленным файлом**. Расхождение должно быть на уровне машинной
точности; если оно больше — рецепт разошёлся с тем, что реально отправлено.

Запускайте через `python -u`, иначе вывод буферизуется и прогресс не виден до
самого конца прогона.

Вклад своего блока признаков и устойчивость к сдвигу уровня площадки:

```bash
python -u src/train.py --cutoffs 6 --blocks windows,lifetime,ratios,platform,unit,ranks --note "без моего блока"
python -u src/train.py --cutoffs 8 --val-cutoff 2025-12-16 --train-cutoffs 2025-06-19,2025-07-19,2025-08-18
```

**Флаг `--rank-stamps` по умолчанию НЕ включать.** Шесть признаков (`tenure`,
`first_ord_ago`, `active_months`, `day_crowd_mean_30/90/365`) монотонно растут
с датой среза и на тесте выходят за обучающий диапазон, а деревья за границу
не экстраполируют. Замена их процентильным рангом внутри среза выигрывала
+0.00036 и +0.00077 на выровненной валидации — **и проиграла 0.00079
на лидерборде** (1.6507540 против 1.6499646 у той же модели без замены).

Флаг оставлен рабочим как воспроизводимый отрицательный результат и как
предупреждение: это единственный известный нам случай, когда эффект прошёл
приёмку по знаку на обоих срезах и всё равно развернулся на public. Разбор —
PLAN.md, раздел 4.

Сейчас существуют шесть блоков: `windows`, `lifetime`, `ratios`, `platform`,
`unit`, `ranks`. Полный список всегда виден в подсказке
`python src/datasets.py --help`.

**Обе руки сравнения запускайте одной командой.** Между пересборками кэша
результаты расходятся на 0.0009 даже при побитово одинаковых признаках —
хватает разницы 1e-12 в таргете от порядка суммирования.

Диагностика и калибровка:

```bash
python -u src/errors.py                 # из каких клиентов складывается RMSLE
python -u src/bias.py                   # смещение уровня и оптимальный сдвиг на трёх срезах
python -u src/calibrate.py --apply submissions/<файл>.csv   # оценка суммарного GMV для жюри
python -u src/tune.py --trials 14 --space broad             # перебор гиперпараметров
python -u src/ensemble.py --val-cutoffs 2026-01-15,2025-12-16 --members mixed
```

Проверки, которые надо гонять перед сдачей:

```bash
python -u src/leak_audit.py             # утечка цели: признаки, вход сетей, порядок срезов
python -u src/doc_audit.py              # команды документов против --help скриптов
python -u src/rebuild_final.py          # пересборка ОБОИХ финальных файлов со сверкой
python -u src/rebuild_comp.py           # пересборка валидационного состава со сверкой
```

Разница между двумя последними важна. `rebuild_final` восстанавливает то, что
**отправлено**; `rebuild_comp` — то, против чего меряются все замеры
направления («партнёр не проходит», «состав в оптимуме»). Второе основание
было невоспроизводимым до 28.08: файлы собирались разовым скриптом, которого
не сохранилось.

`leak_audit` — единственная проверка на класс ошибок, который **улучшает**
метрику и потому метрикой не ловится. Читает журналы веток флагом `--refs`:
работа второй половины команды попадает в main не сразу, а аудит только
по main покрывает ствол, а не работу команды.

Разовые разборы, оставленные воспроизводимыми отрицательными результатами:

```bash
python -u src/prob_compose.py --net yearprob --point comp_jan --cut 2026-01-15
python -u src/probe_cubic.py --gamma 0.0036          # зонд кубической поправки
python -u src/swap_half.py                           # замена устаревшей половины
```

Сетевой флаг `--multi FINE` (ветка `multi-res`) даёт **многомасштабное окно**:
последние `FINE` дней остаются дневными, остальное сворачивается шагом `--bin`.
При `--lookback 364 --bin 7 --multi 91` выходит 39 недельных шагов плюс
91 дневной. Направление проверено и отвергнуто — `docs/jury/A4`.

**Сравнивайте модели только по выровненному RMSLE.** `tune.py` печатает обе
величины и пишет обе в журнал: сырую и с приведением уровня предсказаний
к истинному уровню окна. Второе — это ровно то, что делает бесплатный сдвиг
на сабмите, поэтому выигрыш в уровне на лидерборде **не засчитывается**:
он там уже взят. Ловушка срабатывала трижды и всякий раз завышала результат
(PLAN.md, раздел 2).

Работа с решениями других треков — половины решения живут на разных машинах,
и чтобы посчитать метрику совместного состава, достаточно предсказаний
на одном срезе, без переноса кода и весов:

```bash
python -u src/train.py --cutoffs 6 --ensemble --save-val-pred --name my_ens
python -u src/compose.py --a models/my_ens_valpred_2026-01-15.npz --b models/<чужой>_2026-01-15.npz --wb 0.542
python -u src/net_value.py --base <работающая> --new <проверяемая>   # потолок пользы от чужих предсказаний
python -u src/blend_opt.py --a A.csv --mse-a <RMSLE> --b B.csv --mse-b <RMSLE> --out blend.csv
```

`blend_opt.py` считает результат любой комбинации **уже отправленных** файлов
точно, из их же public-оценок, не тратя ни одной попытки; `--weight` позволяет
взять вес меньше оптимального (оптимум оценён по 50 000 клиентов public,
а применяется к 200 000 private).

`net_value.py` меряет **линейный** потолок: для готового предсказания сети это
честная оценка сверху, а для сырых внутренних величин (скрытое состояние,
эмбеддинги) — нижняя граница, и низкое значение там направление не закрывает.

Зондирование лидерборда — как измерить поправку, которой нет в валидации.
Зондом больше **не измеряют ни уровень, ни растяжение**: уровень выведен
(константа `TEST_LEVEL`) и берётся флагом `--derive-shift`, растяжение
считается из целевой дисперсии. Рабочий порядок для новой модели:

```bash
python -u src/probe_shift.py --derive-shift --source <сырой>.csv          # уровень, бесплатно
python -u src/probe_shift.py --source <сырой>.csv --delta <выведенный> --out lvl.csv
python -u src/probe_shift.py --source lvl.csv --alpha 1.02 --out /dev/null  # только чтобы узнать Var(p)
python -u src/probe_shift.py --source lvl.csv --alpha <sqrt(2.6408/Var)> --out a.csv
```

Зонд с шагом 1.02 остаётся в арсенале на случай, когда целевую дисперсию
взять неоткуда — например у модели принципиально другой силы:

```bash
python -u src/probe_shift.py --solve --alpha 1.02 --var-p <из вывода> --mse0 <RMSLE базы> --mse1 <RMSLE зонда>
```

Третья поправка — кривизна. Порядок тот же, но флаги другие, и применяется она
к файлу, у которого уровень и размах **уже** поправлены:

```bash
python -u src/probe_shift.py --source <откалиброванный>.csv --gamma 0.005 --out probe_q.csv
python -u src/probe_shift.py --solve --gamma 0.005 --var-g <из вывода> --mse0 <RMSLE базы> --mse1 <RMSLE зонда>
```

Без `--var-g` разбор ответа завершится сообщением «для квадратичного зонда
нужен --var-g»: у квадратичного направления своя дисперсия, `--var-p` тут
не подходит.

Четвёртое семейство поправок — **вдоль признака, а не вдоль предсказания**.
Сдвиг, растяжение и кривизна правят предсказание как функцию его самого,
но остаток может зависеть и от клиента:

```bash
python -u src/probe_shift.py --source <база>.csv --feature lt_active_days --step 0.02 --out probe_f.csv
python -u src/probe_shift.py --solve --feature lt_active_days --step 0.02 --mse0 <RMSLE базы> --mse1 <RMSLE зонда>
```

Направление ортогонализуется к константе, предсказанию и его квадрату — иначе
зонд повторил бы уже применённые поправки и сбил их. Нормировано на единичную
дисперсию, поэтому шаг сравним между признаками.

Шаг брать **малым** (1.02 вместо 1.04, 0.005 вместо 0.02): направление заранее
не угадывается — из трёх наших зондов ни один не совпал с ожиданием, — а цена
ошибки растёт как квадрат шага. Зонд кривизны с шагом 0.02 стоил 0.0022 RMSLE,
с шагом 0.005 стоил бы около 0.0001.

### Нейросетевая половина: ЧЕТЫРЕ руки, а не одна

Лучшее решение команды — состав бустинга с сетями, поэтому одним бустингом оно
не воспроизводится. Важнее другое: **сетей в составе четыре, и они разные.**
Прежняя редакция этого раздела приводила только первую и называла её
«нейросетевой половиной» — по ней собиралось решение без трёх рук, включая ту,
что дала рекорд.

Все четыре обучаются на видеокарте, все с распределительной головой на 64 бина.

**Сначала собирается матрица последовательностей — без неё ни одна сеть
не запустится.** Шаг разовый: матрица `клиенты x дни x каналы` строится один
раз на весь период и дальше только нарезается окнами.

```bash
python -u src/seq_data.py        # ОБЯЗАТЕЛЬНО ПЕРВЫМ: матрица 250000 x 409 x 18
```

Пропуск этого шага даёт внятный отказ `нет матрицы seq_train_409x18.npy`,
а не загадочную ошибку, — но пропускать его всё равно нельзя. До 29.08 README
о нём не говорил, и прогон с чистого клона упирался в него на первой же
сетевой команде: путь бустинга проверялся треком B дважды, сетевой — ни разу.

```bash
# 1. Сеть под стекинг: 90 дней дневным шагом. Идёт признаком в бустинг.
python -u src/seq_train.py --lookback 90 --arch gru --static rk_ --bins 64
python -u src/seq_oof_net.py --lookback 90 --static rk_ --bins 64 --seeds 42,13,7 --name netoof_b64
python -u src/train.py --cutoffs 6 --ensemble --net --net-names b64 --final --name lgbm_stk

# 2. ГОДОВАЯ сеть: 364 дня недельным шагом. Главный вклад состава.
python -u src/seq_train.py --lookback 364 --bin 7 --static rk_ --bins 64 --seed 42 --name yearfin_s42
#   то же для сидов 13, 7, 3 -> усредняются в yearfin_avg4

# 3. Сеть БЕЗ статических рангов: 90 дней, флага --static нет намеренно.
python -u src/seq_train.py --lookback 90 --bins 64 --seed 42 --name nostfin
#   то же для сидов 13, 7, 3 -> nost_avg

# 4. Событийная сеть: 364 дня, 96 событий вместо календарной сетки.
python -u src/seq_train.py --lookback 364 --events 96 --static rk_ --bins 64 --seed 42 --name evfin
#   то же для сидов 13, 7 -> ev_avg

python -u src/seq_cmp.py --cut 2026-01-15 --a <контроль> --b <рука>   # сравнение с выравниванием
```

Ориентиры на январском срезе (**сырой** RMSLE, как его печатает сеть):

| рука | конфигурация | сырой | выровненный |
|---|---|---|---|
| годовая, сид 42 | `seq18x364b7` | 1.68202 | 1.66785 |
| без рангов, сид 42 | `seq18x90b1` | 1.71160 | — |
| событийная, сид 42 | `seq18x364e96` | 1.67452 | — |

**Колонка `feat_ver` в `models/experiments.csv` — эталон конфигурации,
а не эта таблица.** Тег читается однозначно: `seq18x364b7` — 18 каналов,
окно 364 дня, шаг 7; `seq18x364e96` — то же окно, но 96 событий вместо шага;
`seq18x90b1` — 90 дней дневным шагом. Если текст документации разойдётся
с журналом, прав журнал: он пишется прогоном, а текст — человеком.

**Третья рука выглядит браком и им не является.** Сеть без статических рангов
хуже базовой на 0.037 — по обычным меркам её следовало выбросить, я и
выбросил её однажды как испорченный замер. Но она даёт **+0.00074** сверх
годовой, потому что, лишённая рангов, вынуждена опираться на одну
последовательность и ошибается в другую сторону. Это главный практический
вывод всей работы: полезен не тот партнёр, кто силён, а тот, чьё отличие
направлено против нашей ошибки.

**`--bins K` — распределительная голова:** вместо одного числа с L2 сеть выдаёт
K логитов, учится кросс-энтропией по номеру бина, а предсказание берётся как
`E[log1p] = Σ pₖcₖ`. Нулю отводится отдельный бин: `log1p(0) = 0` ровно, и там
сидит 46% клиентов. Дало сети +0.0005 и +0.0009 на двух срезах, а через
стекинг +0.00110 и +0.00203 — и заодно сделало решение вероятностным
(разбор и замеры калиброванности — `docs/jury/A3_probabilistic.md`).

Сравнивать руки только через `seq_cmp.py`: сеть печатает **сырой** RMSLE,
а сравнивать можно лишь выровненный, и на распределительной голове это
однажды перевернуло знак (−0.00168 сырым против +0.00063 выровненным).

Окно 90 дней — измеренный оптимум (60 и 180 хуже на обоих срезах). Сидов не
меньше трёх: одиночный прогон сети не меряет ничего на уровне тысячных, разброс
по сидам сопоставим с самим эффектом (PLAN.md, раздел 2).

Файлы `models/netoof_*.npz` в репозиторий не кладутся — они нужны бустингу
для флага `--net`.

Один эксперимент — одна ветка и один PR: так видно, что именно дало прирост,
и так же это увидит жюри в истории. Каждый сабмит `predict.py` пишет строку в

ответа лидерборда впишите в ту же строку `lb_score` — на 5 сабмитах в день и
двух финальных решениях без такого журнала команда быстро перестаёт понимать,
какой файл откуда взялся.

## Постановка и валидация

Таргет — сумма `gmv` за окно `[cutoff, cutoff + 30)`. Тестовый cutoff — 2026-02-14.

Обучающие cutoff'ы идут с шагом 30 дней назад от 2026-01-15 (позже нельзя:
таргет должен целиком помещаться в известные данные). Валидация — на самом
свежем cutoff'е, обучение на более старых, окна таргета не пересекаются.

Метрика RMSLE — это RMSE в шкале `log1p`, поэтому:

* модель обучается на `log1p(target)` с обычным L2-лоссом, ранняя остановка по `rmse`;
* оптимальное предсказание — условное среднее **в логарифмах**, а не `log` от среднего;
* сабмит получается как `expm1(pred_log)` с клипом снизу нулём.

## Модели

* **single** — регрессия `log1p(gmv_30d)` напрямую.
* **two-stage** — `P(покупка) * E[log1p(gmv) | покупка]`. Разложение точное, так как
  `log1p(0) = 0`, поэтому `E[log1p(y)] = p * E[log1p(y) | y > 0]`. Обычно лучше
  ранжирует пользователей (Gini) — это tie-breaker жюри.
* **blend** — веса подбираются на валидации по RMSLE.
* **ансамбль** (`--ensemble`) — одноголовая модель заменяется средним нескольких
  разнородных конфигураций в log1p-шкале. Состав выбирается флагом `--members`:
  `lgb` (умолчание, пять конфигураций LightGBM), `cat`, `mixed` (5 LightGBM +
  2 CatBoost). Отдельные конфигурации-чемпионы между валидационными срезами
  не переносятся, а среднее выигрывает на обоих.
* **поправки калибровки** — сдвиг уровня и растяжение размаха, измеренные
  зондированием лидерборда. Применяются к готовому сабмиту, модель не трогают.

Кроме RMSLE считаются нормированный Gini и относительная ошибка суммарного
предсказанного GMV — оба используются жюри на этапе отбора финалистов.

## Что уже проверено — не тратьте на это время

Шаг срезов 14 дней вместо 30, взвешивание срезов по свежести, перебор
гиперпараметров, CatBoost в составе ансамбля, модель остатка через `init_score`,
признак «GMV в это же окно год назад», праздничные признаки — **всё проверено
и не работает**, с числами и объяснениями в [PLAN.md](PLAN.md), раздел 4.

Там же главное методологическое правило: **эффект меньше 0.002 неизмерим**
одним валидационным срезом, его нужно проверять на двух и принимать только при
положительном знаке на обоих.

## Признаки: как добавить свой блок

Признаки собираются из независимых блоков — так несколько человек добавляют
свои, не встречаясь в мержах. Блок = модуль в `src/features/` с одной или
двумя функциями:

```python
# src/features/my_block.py
import polars as pl
from .registry import aggs_block, derived_block

@aggs_block("my_block")           # выражения внутри group_by("user_id").agg(...)
def my_aggs(cutoff):              # доступны колонки лога и days_ago (>= 1)
    return [pl.col("gmv").filter(pl.col("days_ago") <= 45).sum().alias("gmv_sum_45")]

@derived_block("my_block")        # выражения поверх готовых агрегатов
def my_derived():
    return [(pl.col("gmv_sum_45") / (pl.col("gmv_sum_365") + 1e-6)).alias("gmv_share_45")]
```

плюс строка `from . import my_block` в конце `src/features/__init__.py`.

Вклад своего блока меряется тем же `train.py` с `--blocks`:

```bash
python src/train.py --blocks windows,lifetime,ratios,platform,unit,ranks           # без своего
python src/train.py --blocks windows,lifetime,ratios,platform,unit,ranks,my_block  # с ним
```

Кэш выборок привязан к хешу кода признаков и к набору блоков, поэтому после
правки он пересобирается сам — чистить руками ничего не нужно.

## Что уже есть в признаках

Всё считается строго по данным **до** cutoff'а:

* оконные агрегаты за 7/14/30/60/90/180/365 дней: суммы GMV (общий, поиск, каталог),
  заказы, добавления в корзину, поисковые запросы, число активных дней и дней с покупкой;
* рецентность: дней с последнего события / заказа / добавления в корзину / поиска,
  а также разрыв между двумя последними покупками;
* BTYD-подобные величины: `T` (tenure), `t_x`, частота покупок, средний межпокупочный
  интервал и «просрочка» относительно него;
* тренды (7/30, 30/90, 90/365) по деньгам, активности и заказам;
* конверсии воронки (поиск → корзина → заказ), средний чек, доля Поиска в GMV;
* доли пользователя в суточном GMV площадки — не зависят от уровня площадки,
  который за год менялся вдвое (блок `platform`);
* юнит-экономика и регулярность: цена единицы товара, активные недели и месяцы,
  разброс межпокупочных пауз, выходные, брошенные корзины (блок `unit`);
* процентильные ранги 27 ключевых величин внутри среза (блок `ranks`) — они
  снимают привязку к абсолютному уровню, ничего не выбрасывая, и дали
  крупнейшее улучшение признаков за всю работу.
