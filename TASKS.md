## Трек A — ноутбук, CPU: сабмиты, калибровка, учёт

**A1. Дежурная перекалибровка.** Если трек C меняет вес сети или архитектуру —
модель другая, и поправки надо получить заново. Порядок:

```bash
python -u src/probe_shift.py --derive-shift --source <новый>.csv      # сдвиг, бесплатно
python -u src/probe_shift.py --source <новый>.csv --alpha 1.02 --out probe_a.csv
python -u src/probe_shift.py --solve --alpha 1.02 --var-p <из вывода> --mse0 <RMSLE базы> --mse1 <RMSLE зонда>
```

Шаг зонда — **малый** (1.02, не 1.04): направление не угадывается, а цена
ошибки растёт как квадрат шага. Ожидание: при малом весе сети растяжение снова
понадобится, при большом — нет (сеть сама расширяет размах).

**A2. Учёт сабмитов и финальный выбор.** Журнал `submissions/log.csv` ведётся
автоматически, `lb_score` вписывается руками. К концу этапа в нём должно быть
видно, какие два файла выбраны финальными и почему.

**A3. Проверить, что финальные решения действительно отмечены** на платформе
до закрытия этапа. Процедурный риск, который стоит дороже любых 0.002.

## Трек B — ноутбук, CPU: материалы жюри

**B1. Воспроизводимость с чистой машины.** Клонировать репозиторий в пустую
папку, пройти README сверху вниз, убедиться, что решение собирается без правок
и без подсказок. Всё, что придётся додумывать, — дописать в README.

**B2. Таблица tie-breaker'ов.** Жюри смотрит Gini по предсказаниям и RMSPE
суммарного GMV. Свести по финальным кандидатам:

```bash
python -u src/calibrate.py --apply submissions/<файл>.csv
```

Известно: калибровка **не меняет Gini** (все три поправки сохраняют порядок
клиентов, ранговая корреляция 1.000000), а у бленда Gini на январе 0.7348
против 0.7378 у чистого бустинга — то есть по ранжированию бустинг чуть лучше.

**B3. Черновик питча.** Что показывать, кроме результата:

* зондирование лидерборда как измерительный прибор: три поправки, каждая
  предсказана до пятого знака и подтверждена ответом;
* вывод уровня тестового окна, после которого зонд на уровень не нужен никому;
* тринадцать честно задокументированных отрицательных результатов с числами —
  редкость на таких соревнованиях;
* найденный предел сравнимости прогонов (0.0009 между пересборками кэша) и
  правило двух валидационных срезов.

## Трек C — ПК с видеокартой: вторая финальная кандидатура

**C1. Вариант бленда с бо́льшим весом сети — главная задача трека.**
Текущий вес 0.25 подобран под 50 000 клиентов public. Private вчетверо больше
и другая, поэтому вариант с весом около 0.35–0.40 — это страховка, а не потеря,
даже если на public он чуть хуже.

Обоснование измерено с двух сторон: все кандидаты внутри бустингового семейства
коррелируют на 0.9992–0.9997, то есть два лучших файла — это одно решение
дважды. **Настоящую непохожесть в команде даёт только сеть.**

**C2. Если остаётся время — улучшать сеть, а не бустинг.** Это единственное
место, где ещё возможен эффект крупнее порога: бустинг на этих признаках
выбирает практически всю доступную информацию, что подтвердили обе половины
команды независимо.

## Общие правила

* **Порог 0.002.** Эффект меньше — проверять на двух валидационных срезах
  (2026-01-15 и 2025-12-16) и принимать только при положительном знаке на обоих.
* **Обе руки сравнения — одной командой на одной версии кэша.** Между
  пересборками кэша числа расходятся на 0.0009 даже при одинаковых признаках.
* **Один эксперимент — одна ветка и один PR**, в описании строки из
  `models/experiments.csv` до и после.
* **Журналы обязательны.** `train.py` и `predict.py` пишут их сами; после ответа
  лидерборда впишите `lb_score` руками в `submissions/log.csv`.
* **Не трогайте чужие файлы.** Признаки разложены на блоки именно для этого:
  свой модуль плюс одна строка импорта в `src/features/__init__.py`.
* **Данные и веса в git не кладём** — только код и журналы.
