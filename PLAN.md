# План работ

Базовая линия зафиксирована: **RMSLE 1.6852** на валидации (cutoff 2026-01-15),
Gini 0.738. Наивная авторегрессия из baseline организаторов — 2.195, константный
ноль — 3.204. Всё дальнейшее сравнивается с 1.6852.

## Единый протокол — иначе числа команды несравнимы

Любой эксперимент меряется одинаково, иначе прирост невозможно отличить от
разницы в постановке:

* обучение на 5 срезах (2025-08-18 … 2025-12-16), валидация на 2026-01-15;
* метрика — `rmsle_blend` из `models/experiments.csv`, туда `train.py` пишет
  строку сам (коммит, версия признаков, число признаков, все три RMSLE);
* нельзя сравнивать свой прогон с чужим числом из чата — только строки журнала
  с одинаковым `feat_ver` или с явной пометкой, что менялось.

Кэш признаков привязан к хешу `features.py` + `config.py`: после изменения кода
признаков он пересоберётся сам (~20 секунд на срез). Руками ничего чистить не надо.

## Направления, по убыванию ожидаемой отдачи

### 1. Сезонность тестового окна (никто из идущих по baseline этого не делает)

Тест — 14 февраля … 15 марта: 23 февраля и 8 марта, два крупнейших пика года.
Ни один обучающий срез их не покрывает, поэтому модель их структурно не видит.
Что делать: признак «GMV пользователя в это же календарное окно 2025 года»
(данные с 2025-01-01 — окно целиком есть), общий сезонный индекс дня, доля
пользователя в дневном GMV площадки.

### 2. Больше обучающих срезов

Шаг 14 дней вместо 30 — вдвое больше примеров ценой пересечения окон таргета.
Проверить, не съедает ли корреляция между пересекающимися таргетами весь прирост.
Отдельно: взвешивание срезов по близости к тесту.

### 3. Гиперпараметры и ансамбль

Ранняя остановка сейчас срабатывает на 149-й итерации при lr=0.03 — это признак
сдвига распределения между срезами, а не сходимости. Пробовать: `num_leaves`
меньше, lr ниже с большим числом раундов, сильнее регуляризацию. Дальше —
CatBoost и XGBoost на GPU и бленд трёх бустингов.

### 4. Нейросетевая ветка

Организаторы прямо намекают на токенизацию дневного поведения. Практичный путь:
последовательность дневных событий → GRU/трансформер → предсказание таргета,
а скрытое состояние дополнительно отдать бустингу как признаки. Даже средняя
сеть в бленде обычно даёт 0.01–0.02 RMSLE.

### 5. Калибровка суммарного GMV (для жюри, не для лидерборда)

RMSLE-оптимальное предсказание систематически занижает суммарный GMV (сейчас
8.9 млн против ~21 млн фактических) — это математика метрики, а не ошибка.
В сабмит поправка не идёт: RMSLE сразу ухудшится. Но у жюри в tie-breaker'ах
есть сравнение суммарного GMV по RMSPE, поэтому нужна отдельная калиброванная
оценка суммы (Tweedie-модель или поправка на дисперсию) — в репозитории и на питче.

## Разделение, чтобы не конфликтовать в одних файлах

| Трек | Файлы | Железо |
|---|---|---|
| Признаки (1) | `src/features/<свой блок>.py` — по модулю на человека | CPU |
| Валидация и калибровка (2, 5) | `config.py`, `train.py`, `metrics.py` | CPU |
| Бустинги и тюнинг (3) | `models.py`, конфиги параметров | GPU (5060/5070) |
| Нейросеть (4) | отдельный модуль, не трогает существующие | GPU (5060/5070) |
| Сборка ансамбля и сабмиты | `predict.py`, журналы | любое |

Признаки уже разложены на независимые блоки (`src/features/`), поэтому в один
файл никто не пишет: свой блок — свой модуль плюс одна строка импорта. Вклад
блока меряется флагом `--blocks` (см. README). Это снимает основной источник
конфликтов при параллельной работе.

## Правила работы

* Один эксперимент — одна ветка и один PR. В описании PR: строка из
  `experiments.csv` до и после.
* В `main` попадает только то, что не ухудшает базовую линию.
* Сабмитов 5 в день **на всю команду**. Договорённость: 3 слота под проверенные
  улучшения (прирост на валидации от 0.003), 2 — под разведку.
* Каждый сабмит пишется в `submissions/log.csv` автоматически; после ответа
  лидерборда в ту же строку руками вписывается `lb_score`.
* Данные и веса в репозиторий не кладём — только код и журналы.

## Выбор двух финальных решений

Соотношение public/private — 20/80, то есть на public всего 50 000 клиентов и
переобучиться под него легко. Разумный набор: одно решение — лучшее по валидации,
второе — самое устойчивое (лучшее среднее по нескольким валидационным срезам,
а не по одному). Выбирать по валидации, а не по public-лидерборду.
