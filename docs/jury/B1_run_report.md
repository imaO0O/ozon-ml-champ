## Два дефекта, найденных прогоном — статическим чтением не видны

**Оба починены в `main`.** Описание оставлено как есть — оно показывает, что
именно нашёл прогон на чистой машине; ниже по каждому указано, чем закрыт.

### 1. `predict.py` падает трейсбеком вместо своего же сообщения

Сценарий — самый частый у новичка: обучил без `--final`, пошёл делать сабмит.

```
$ python -u src/train.py --cutoffs 3 --rounds 100 --name nofinal
прогон без --final: веса не сохранялись
$ python -u src/predict.py --name nofinal
FileNotFoundError: models/nofinal_meta.json
```

В `predict.py` есть заготовленная вежливая проверка
(`модели '...' обучены без --final...`), но она **недостижима**: файл
`_meta.json` вообще не создаётся без `--final`, поэтому чтение падает
строкой выше. Лечится одной проверкой существования файла перед чтением.
Файл чужой, поэтому правка не вносилась — только зафиксирована.

### 2. `datasets.py --clean` всегда удаляет кэш с `--history`

`clean_stale_cache` решает, что оставить, по `p.stem.endswith(keep)`. У файлов
с обрезанной историей имя кончается на `_h180`, а не на хеш версии,
поэтому проверка не срабатывает никогда. Продемонстрировано на одной
и той же версии признаков `eea7602e`:

```
$ python -u src/datasets.py --cutoffs 1 --history 180 --clean
освобождено 2 МБ, оставлена версия eea7602e
[2026-01-15] 7,733 строк x 245 колонок — пересобран тем же запуском
```

Скрипт удалил свежий кэш и тут же его перестроил. На боевых данных
это не 2 МБ и полсекунды, а сотни мегабайт и минуты на каждый срез.
Затрагивает воспроизведение отрицательного результата про одинаковую глубину
истории (PLAN, раздел 4).

## Численная проверка ключевого утверждения B2

Утверждение «калибровка не меняет Gini» проверено на реальном векторе
предсказаний (7 887 значений, размах log1p от 0.221 до 8.329):

| поправка | порядок клиентов сохранён |
|---|---|
| сдвиг +0.0578 | да |
| растяжение 1.0545 | да |
| кривизна −0.01325 | да |
| все три подряд | да |

Производная поправки кривизны `1 + γ(2u − c)` при c = 1.9957 лежит
в диапазоне **от 0.8627 до 1.0775** — всюду положительна. Нуля она достигла
бы при u = 38.7, тогда как наблюдаемый максимум u = 6.18. Запас по
монотонности шестикратный, то есть утверждение верно не случайно, а с
большим запасом. На вопрос жюри «а вдруг квадратичная поправка портит
ранжирование» есть прямой численный ответ.

## Прогон на БОЕВЫХ данных, 29.08 — то, чего синтетика показать не могла

Выполнен треком A на своей машине; это **не заменяет** независимый прогон
трека B, потому что не проверяет переносимость между железом и версиями
CUDA. Проверяет другое: самодостаточен ли репозиторий и совпадают ли числа.
Оба вопроса на синтетике не проверялись — там 7 887 клиентов и числа
несопоставимы с журнальными по построению.

### Два блокера, найденных сразу

**1. Ни одна сеть не запускалась с чистого клона.** Раздел README с командами
сетей не говорил собрать матрицу последовательностей, и первая же команда
падала: `нет матрицы seq_train_409x18.npy`. `seq_data.py` упоминался только
в перечне файлов.

Прогоны 13.08 и 21.08 этого не поймали, потому что их чек-лист покрывал
**только путь бустинга** — `seq_train` в нём нет вовсе. Сетевой путь, на
котором стоит чемпион и три компоненты состава из пяти, с чистого клона
не проверялся ни разу. README исправлен 29.08.

**2. Документированная команда бустинга не имеет эталона в журнале.**
`train.py --cutoffs 6 --ensemble --final` — головная команда README.
Ансамблевых прогонов в журнале тринадцать, но **на текущей версии признаков
`9db461e7` — ни одного** (56 прогонов lgbm, ансамблевых ноль). Член жюри
получает число, которое сверить не с чем. Первое такое число получено
и записано: `single 1.68141`, `blend 1.68178`, `Gini 0.7387`.

### Что воспроизвелось и насколько точно

**Признаки — побитово, все 242, на всех семи срезах.**

    срез                 242 признака    target
    2025-08-18           max 0.0e+00     1.82e-12  (отн. 9.6e-17)
    2025-12-16           max 0.0e+00     3.64e-12  (отн. 1.2e-16)
    2026-01-15           max 0.0e+00     1.82e-12  (отн. 3.4e-17)
    2026-02-14           max 0.0e+00     0.00e+00

Расходится **только цель**, на относительных 10⁻¹⁶ — машинный эпсилон
от порядка суммирования в группировке. Тестовый срез, где цели нет, совпал
побитово: это контроль самого объяснения, а не совпадение.

**Годовая сеть — тоже побитово.**

    предсказания        max |разница| 0.000e+00 на 250 000 клиентов
    выровненный RMSLE   1.6678507 против 1.6678507
    сырой RMSLE         1.68202 против 1.68202
    порог трека C       0.001 — не понадобился

### Бустинг: расхождение измерено и оказалось впятеро меньше заявленного

Эталон создан той же командой в рабочем репозитории, где цель отличается
на 1.8e-12. Сравнение с клоном:

    величина            эталон       клон     разница
    rmsle_single       1.68159    1.68141    -0.00018
    rmsle_blend        1.68190    1.68178    -0.00012
    gini_blend          0.7386     0.7387    +0.00010
    итераций до остановки  222        239    +17

**0.00018 — и это ВНУТРИ шумового пола трека C** (0.00081 на январе).
То есть бустинг с чистого клона воспроизводится в пределах допуска,
установленного независимо.

README утверждал 0.0009 — число из более раннего замера на одиночной модели.
У ансамбля из пяти конфигураций расхождение впятеро меньше: усреднение гасит
разброс точки остановки. README исправлен 29.08.

**И это уточняет утверждение, которое README делал без разбора.** Там сказано,
что расхождение 1e-12 в цели даёт расхождение результата 0.0009. Верно —
**для бустинга**, который считает в float64. Сети учатся в **bf16**, где
мантисса даёт три десятичных знака, и разница на двенадцатом исчезает при
конверсии. Поэтому сеть воспроизводится точно, а бустинг — нет. Различия
между двумя половинами конвейера прежде не проводилось.

### Что остаётся непроверенным

Переносимость между машинами. Здесь всё считалось на той же карте
(RTX 5070), тем же CUDA и тем же окружением. Побитовое совпадение сети —
свойство детерминизма **на одной машине**, и переносить его на другую нельзя:
шумовой пол трека C (0.00081 январь, 0.00155 декабрь) измерен именно между
режимами точности и остаётся действующим порогом для чужого железа.

### Третий блокер, найденный на последнем шаге: инструкция воспроизводила выбывшую конфигурацию

`seq_oof_net` и стекинг прошли, но результат разошёлся с журналом: клон дал
`single 1.67944` против `stk2_jan 1.67869`. Разбор занял четверть часа
и дал больше, чем сам прогон.

**OOF-признаки воспроизвелись не все.** Из восемнадцати прогонов одиннадцать
совпали побитово, семь разошлись — до 4.17 в log1p. Механизм установлен
без единого исключения:

    эпоха совпала (11 прогонов)  -> предсказания 0.000e+00
    эпоха разошлась (7 прогонов) -> предсказания расходятся

Это не недетерминизм. Оригиналы сделаны 20.08 на коммите `5b6874d`,
а `seq_train.py` менялся с тех пор **19 раз**, включая починку ранней
остановки по выровненной метрике. Старые прогоны останавливались
на **2-й и 4-й эпохе из двадцати** — ровно тот дефект, который трек C
починил на +0.00112.

**И отсюда главное.** README велел строить `netoof_b64` и стекать
на `--net-names b64`. Но стекинг в составе стоит на **`b64a`** — проверено
по `lgbm_stk2_meta.json`, где признаки называются `net_b64a_rank`
и `net_b64a_centered`. Набор `b64a` сделан 24.08, уже после починки.

Значит член жюри, идущий по инструкции, воспроизводил **не наше решение**,
а его предшественника на недоученных сетях. Расхождение 0.00075 объясняется
этим целиком. README исправлен 29.08.

**Класс дефекта тот же, что нашёлся сегодня в `A3` и в `rebuild_final`:
документ описывает выбывший артефакт.** Здесь он был опаснее прочих, потому
что прятался не в тексте, а в имени файла — и обнаружился только сквозным
прогоном.
