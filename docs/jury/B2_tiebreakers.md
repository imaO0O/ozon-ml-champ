# B2. Таблица tie-breaker'ов

Жюри при отборе финалистов смотрит, помимо RMSLE, два дополнительных
показателя: нормированный Gini по предсказаниям и относительную ошибку
суммарного предсказанного GMV. Здесь сведены оба по всем кандидатам на
финальные решения.

Числа взяты из журналов `models/experiments.csv` и `submissions/log.csv`,
источник каждого указан. Ничего не пересчитывалось на глаз.

## Откуда что берётся

**Gini по сабмиту вычислить нельзя** — `metrics.gini_norm` требует истинных
значений, а для тестового окна их нет и не будет до раскрытия private.
`calibrate.py` его тоже не печатает. Поэтому Gini здесь — **валидационный**,
со среза 2026-01-15: колонка `gini_blend` в `experiments.csv`, она же
`val_gini` в `log.csv`.

**Ошибка суммы** в колонке «сырая» — это `sum_bias_blend` на той же валидации,
то есть насколько предсказанная сумма GMV расходится с фактической. Знак
всюду отрицательный: модель занижает сумму примерно вдвое.

**Оценка суммарного GMV теста** получена умножением суммы предсказаний файла
на скалярный множитель ×2.002 из `calibrate.py`. Оговорки к этому числу —
в конце документа, они существенные.

## Что из этой таблицы следует

**Tie-breaker'ы расходятся с основной метрикой.** По RMSLE лучший файл —
бленд сети с бустингом. По ранжированию клиентов он **хуже** чистого бустинга:
0.7348 против 0.7378. Если жюри при равенстве смотрит Gini, наш лучший по
метрике файл проигрывает нашему же второму. Это надо не прятать, а озвучить
и объяснить механизмом: сеть добавляет независимую дисперсию, что улучшает
попадание по величине и слегка размывает порядок.

**Разброс Gini между бустинговыми кандидатами неразличим.** 0.7383, 0.7378,
0.7376 — разница 0.0007 при том, что две случайные половины по 125 000
клиентов расходятся на 0.007 RMSLE (PLAN, раздел 6). Выбирать между ними
по Gini бессмысленно, и говорить, что какой-то из них «лучше ранжирует»,
некорректно.

**Главный риск — ошибка суммы.** Сабмит по построению занижает суммарный GMV
примерно вдвое: RMSLE оптимизируется условным средним **логарифмов**, и
`expm1` от него систематически ниже условного среднего самой величины. Если
жюри считает относительную ошибку суммы прямо по нашему csv, мы получаем
около −50% при любом кандидате. Вносить поправку в сабмит нельзя — RMSLE сразу
ухудшится. Значит откалиброванную оценку суммы нужно подавать **отдельно**,
вместе с объяснением, почему она не совпадает с суммой по файлу.

Подтверждение переносимости поправки: множители подобраны на январском срезе,
проверены на декабрьском, ошибка суммы падает с 56% до 12.7% вне подгонки
(PLAN, раздел 5). Скалярная поправка переносится лучше подецильной.

**Калибровка не меняет Gini.** Все три поправки монотонны по предсказанию,
поэтому порядок клиентов сохраняется, а Gini зависит только от порядка. Для
сдвига и растяжения это очевидно. Для кривизны проверяется прямо: поправка
`p + γ·g`, где `g = u² − c·u` после ортогонализации, имеет производную
`1 + γ·(2u − c)`; при γ = −0.01325 и наблюдаемом размахе `u` она остаётся
заведомо положительной, то есть преобразование монотонно. Это согласуется
с измеренной ранговой корреляцией 1.000000.

Практический вывод: **калибровку можно применять, не опасаясь за tie-breaker
по ранжированию.** Она улучшает RMSLE и оценку суммы, а Gini оставляет тем же.

## Оговорки к оценке суммарного GMV — озвучивать вместе с числом

Число 21.4 млн (или 20.15 млн для актуального финального файла) — это
**оценка сверху**, и на то две независимые причины:

**Двойной учёт поправки.** Множитель ×2.002 измерен на некорректированных
предсказаниях, а применяется к уже сдвинутым и растянутым — часть поправки
учитывается дважды.

**Множитель измерен на другой модели.** `calibrate.py` обучает одиночную
конфигурацию `BASE_PARAMS`, а множитель затем умножает предсказания
ансамблевого откалиброванного сабмита. Это не та модель, к которой поправка
прикладывается.

В пользу оценки говорит перекрёстная проверка: фактический суммарный GMV
январского окна был около 21 млн, а зонд лидерборда показал, что тестовое
окно активнее ожиданий модели. Прежняя оценка 17.45 млн по
некорректированному сабмиту выглядит заниженной.

## Как пересобрать таблицу

Gini и ошибка суммы — из журналов, прогонов не нужно: колонки `gini_blend`
и `sum_bias_blend` в `models/experiments.csv`, они же `val_gini` и
`val_sum_err` в `submissions/log.csv`.

Оценка суммарного GMV — отдельным прогоном на файл (обучает две модели
заново, это минуты, а не секунды):

```bash
python -u src/calibrate.py --apply submissions/<файл>.csv
```

Путь задавать относительно корня репозитория: абсолютный путь на дисках
кроме `C:` в текущей версии `calibrate.py` обрабатывается неверно.
